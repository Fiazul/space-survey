# Ship roster + replaceable modules (2026-09-26)

Seven procedurally authored hulls replace the five downloaded/hand-styled models. Hulls,
weapons and landing pads are separate GLBs joined by NAMED SOCKETS, so weapons and pads
are swappable upgrades. Everything is generated by Blender scripts in `tools/blender/`
(Blender 4.2, `blender -b --python <script>`), never hand-edited in the editor.

## Coordinate contract (as seen in Godot after import)

- Nose points **-Z**, up is **+Y**, right is **+X**. Origin at hull centre of mass.
  Blender authors model nose along Blender **+Y** (glTF export maps Blender +Y → Godot -Z; verified 2026-09-26: empty at Blender (0,1,0) lands at Godot (0,0,-1)).
- 1 Blender unit = 1 m. `Ship.fit_model` rescales at runtime; proportions are what matter.
- Triangle budget: hull ≤ 25k tris, module ≤ 3k tris (Android).

## Sockets (glTF empties, imported as `Node3D`, names exact)

| Name | Count | Orientation | Consumer |
|---|---|---|---|
| `SOCKET_WEAPON_<n>` | per table | empty **-Z** = fire direction | weapon module attaches here |
| `SOCKET_BOOSTER_<n>` | per table | empty **+Z** = exhaust direction, origin at nozzle mouth | plume/torch rig |
| `SOCKET_RCS_<n>` | per table | empty **+Z** = exhaust direction | sub-booster puffs |
| `SOCKET_PAD_<n>` | per table | empty **-Y** = deploy direction, origin on hull skin | landing pad module attaches here |
| `SOCKET_LANDJET_<n>` | 4–8 | **-Y** | `LandingThrusters` belly outlets |

`<n>` starts at 0. Left/right pairs are mirrored (even = -X side, odd = +X side).

## Modules

Two sets each, tier-agnostic (any module fits any socket of its kind):

| File | Origin | Extra empties |
|---|---|---|
| `assets/modules/weapon_mk1.glb`, `weapon_mk2.glb` | at attach point, barrel toward -Z | `MUZZLE` at emitter tip |
| `assets/modules/pad_mk1.glb`, `pad_mk2.glb` | at attach point, deploys toward -Y | `FOOT` at ground contact |

Module length reference: weapon ≈ 6 m barrel, pad ≈ 4 m stroke. Runtime scales modules by
hull length (`length_km * factor`), never per-hull.

## Runtime (integration slice, follows the asset slices)

- `SHIP_MODELS` lists the seven hulls in tier order with `"modular": true`; the old five
  entries and their per-hull styler branches are retired.
- A single socket-driven styler replaces per-hull socket constants: walk the imported
  scene, collect sockets by prefix, attach modules, wire plume rigs.
- Unlock: tier `t` unlocks when `GameState` progression reaches `SHIP_UNLOCK[t]`
  (a tunable constant table); tier 1 always unlocked.
- Module choice per kind persisted in `GameState` (`weapon_set`, `pad_set`).

### Runtime as built (2026-09-26)

- Unlock thresholds: `GameState.SHIP_UNLOCK = [0, 1, 2, 4, 6, 9, 12]`, counted as distinct systems in
  `GameState.visited` excluding Sol (Sol is always visited, so counting it would unlock tier 2 at boot).
  `Ship.swap_ship` refuses locked tiers; the hangar row shows "Locked: reach N systems".
- Module set keys: `GameState.weapon_set` / `GameState.pad_set`, each `"mk1"` (default) or `"mk2"`,
  persisted in `profile.cfg` `[player]`. `Ship.set_weapon_set(key)` / `set_pad_set(key)` rebuild
  `ShipSystems` in place (gear/hardpoint state carries over); the hangar shows WEAPONS / LANDING PADS
  MK1|MK2 toggles under the colour picker.
- Module scale: weapon = `length_km * 0.0145` per module metre (~9% of hull length), pad =
  `length_km * 0.012` (stroke ~5.5%); every foot lands on one shared plane at least 1.2% of hull length
  below the hull, so pads on high sockets are scaled up uniformly to reach it.
